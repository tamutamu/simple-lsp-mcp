# コーディングエージェントの行動・必要情報・LSP/MCP適用表

2026-10-25。**設計の起点はLSPの機能ではなく、エージェントの行動と意思決定。** 必要な情報が通常の `rg`、ファイル読み書き、ビルド、テスト、Gitで得られるなら、Simple LSP MCPに新しいツールを増やさない。

判定：**LSP**＝意味解析で直接取得、**LSP＋ソース**＝意味解析で対象を特定して実際のコードを返す、**通常**＝既存のコーディング/外部ツールが適切、**判断**＝エージェントの推論（LSPで断定しない）。

## 2. MCPが返す情報の仕様

| エージェントの質問 | 推奨MCP | **デフォルトで必要な情報だけ** | 要求時だけ拡張 |
|---|---|---|---|
| このファイルに何がある？ | get_document_symbols | 共有path、名前、種類、行、ネスト、symbol_id | detail=full で全LSPノード |
| この関数は何をしている？ | inspect_symbol | 実コード本文、ファイル、範囲、切捨て有無 | view=edit / signature / location、max_lines |
| このAPIの宣言は？ | inspect_symbol | 宣言ヘッダと識別子 | view=signature |
| この識別子はどこ？ | get_definition / get_declaration / get_type_definition / inspect_symbol | 正確なpath + range | source は特定シンボルにだけ要求 |
| どこから参照される？ | find_references | path + range、完全性・件数 | relation_view=lines でソース行追加 |
| 参照コードは何をしている？ | find_references | 参照位置と一致する実ソース行 | relation_view=lines |
| この型の実装・呼出先は？ | find_implementations / hierarchy | 隣接する関係だけ、シンボルと位置 | 必要なら次段を別途取得 |
| この式の型は？ | get_hover | 該当する型や説明 | 長い文書は必要時に確認 |
| 何が壊れている？ | get_diagnostics | severity、code、message、位置 | severity/limit で絞る |
| 変更を安全に適用できる？ | rename / code action | 対象ファイル・編集範囲、プレビュー | apply=true は明示操作 |

**返すべきでないもの：** 全ファイル本文をデフォルト送信、関数内ローカル変数の大量列挙、使わない範囲/パスの重複、無制限のコールグラフ、勝手に生成したコード説明、テスト実行済みという根拠のない主張。

## 3. 選定の判断基準

1. **文字列で十分か**：十分なら `rg`。LSPに仕事を奪わせない。
2. **意味的同一性が必要か**：同名の別宣言、オーバーロード、interface、型、呼出関係ならLSP。
3. **位置だけで意思決定できるか**：できるなら位置のみ。コードを付けない。
4. **実装コードが必要か**：正確なシンボルをLSPで特定して、その**実ソース**を限定返却。位置だけ返して別途同じコードを読ませない。
5. **複数のコード片が必要か**：参照箇所と実ソース行を小さく併記。全文をすべて展開しない。
6. **この情報が完全か**：LSP検索未完、同期の遅れ、切捨て、権限によるキャンセルを明示する。部分結果を完全と偽らない。
7. **書き込みか**：プレビューと編集の承認を区別する。MCPが普通のファイル編集やテストランナーを重複実装しない。

## 4. 実装・効果測定の基準

- `get_document_symbols`：軽量なファイル構造一覧を維持。
- `inspect_symbol`：`view=source|signature|location` を追加。コードはLSPが指定した対象の実ソース。上限と `meta.truncated` 必須。
- `get_definition` / `find_references` / `find_implementations` / `get_declaration` / `get_type_definition`：位置のみを基本とし、`relation_view=lines` では実際のコード行を返す。
- これ以外の行動は既存のLSP基礎ツール・通常コーディングツールに任せる。機能を作るための機能は追加しない。
- 正しさは Go テスト・実Go/Python/TypeScript LSP・MCP経由のリクエストで確認する。
- 開発生産性は独立採点つきCodex A/Bで検証する。旧18ツールでの36試行は合格率18/18同士、平均時間66.08秒対70.01秒、入力トークン307,843対477,106。新設計の再評価はCodex上限で**4試行だけ完了**。効果が出たとはまだ言えない。
- `rename_symbol` のCodex承認キャンセル11件は別問題。成功した通常編集をLSPリネームの成果と数えない。

重要な区別：**LSPの提供可能情報**と**コーディングエージェントが必要とする情報**は同義ではない。上の行動表と情報契約を変更の起点とする。

## 5. 編集文脈の追加検証（2026-10-25）

- MCP実応答で \`inspect_symbol(view=edit)\` を検証した。FastAPIの \`read_items\` は本体と \`@router.get\` デコレータ、\`router = APIRouter(...)\` とそのimportなどを合計1,763バイトのJSONで返す。単一の実装では \`get_user_by_email\` が594バイト、TSの \`ItemsTable\` が524バイト。
- 参照識別子に基づいて、**同一ファイルの実際のimport文と単純なモジュール代入文だけ**を選ぶ。輸入定義の実行時条件、動的import、遠隔依存、複数ファイルの制御フローまで完全に解析したわけではない。完全性を偽らない。
- 必要な関連テストは引き続きテストファイルから取得する。MCPで独自のテスト実行環境やGit操作を重複実装しない。
- [Codexの独立採点つき再評価](benchmarks/fastapi-codex-edit-context-2026-10-25.md)では返却テキストの削減を確認したが、入力トークンと作業時間は改善していない。MCP利用のみを成功条件としない。
