# simple-lsp-mcp 実開発サイクル9：読み取り専用の小規模ツール構成（2026-11-13）

## 問題と対策

通常のCodex用`coding`プロファイルには14のMCPツールがあり、読み取り専用の調査でも`rename_symbol`などの書き込み可能ツールや不要な診断定義がモデルに提示されます。

対策として、読み取り専用の意味解析・コード調査に必要な10ツールだけを公開する**任意の`--tool-profile analysis`**を実装しました。既定の`coding`と`full`には変更していません。Codex app-serverから直接取得したツールカタログの実測値は次のとおりです。

| プロファイル | ツール数 | ツール定義JSON |
|---|---:|---:|
| 従来の`coding` | 14 | 15,902バイト |
| 新しい`analysis` | 10 | 11,987バイト |

**カタログは24.62%縮小**しました。これはモデル入力トークンや請求費用が同じ割合で減った証明ではありません。

## 実際のCodexによる検証

Goの`document.Notifier`の実装型を正確に列挙する開発調査S01を、同一モデル・同一初期Git状態・独立した受入採点を用いてCodex単体とLSP併用で比較しました。各フェーズで両条件は合格しました。

| フェーズ | 指標 | Codex単体 | LSP併用 |
|---|---|---:|---:|
| 修正前・14ツール | 作業時間 | 29.244秒 | 39.378秒 |
| 修正前・14ツール | 総入力トークン | 79,434 | 130,667 |
| 修正前・14ツール | モデル起点のLSP呼び出し | 0 | 2（`find_implementations`） |
| 修正後・10ツール | 作業時間 | 38.102秒 | 35.675秒 |
| 修正後・10ツール | 総入力トークン | 120,154 | 131,978 |
| 修正後・10ツール | 非キャッシュ入力トークン | 14,682 | 15,242 |
| 修正後・10ツール | モデル起点のLSP呼び出し | 0 | 1（`find_implementations`） |

修正後の1ペアでは時間が6.37%短縮し、実際のモデル起点LSP呼び出しは1回に減りました。一方、**総入力トークンは9.84%増加、非キャッシュ入力は3.81%増加**。キャッシュ済み入力の価格を通常入力の10%と仮定した入力費用相当値も、25,229対26,916でLSP側が**6.69%悪化**しています。絶対額の請求料金ではありません。

これは1回限りの確率的なペア比較です。時間短縮や費用削減をツール構成変更による因果効果と断言しません。**実機能の正しさと不要なツール定義の削減を確認した**ことが本サイクルの成果です。

## 反証も記録

同じ10ツール構成で別のGo参照ファイル調査S02も実行しました。モデルはMCPを1回も呼ばず、シェル経由の`gopls references`で回答しました。回答自体は合格でしたが、**simple-lsp-mcpによる改善効果の証拠ではないため、200サイクルの進捗には含めていません**。この結果を利用して有利な数値だけを集めることはしません。
