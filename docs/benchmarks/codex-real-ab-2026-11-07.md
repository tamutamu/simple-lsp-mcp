# Codex実開発A/B評価（2026-11-07）

## 概要

Codex単独（baseline）と、同一Codexに最新版のsimple-lsp-mcpを接続した条件（MCP）を比較した。
**実際にLSPが呼び出された**トレースを確認した。比較は同時進行、同一タスク文、同じFastAPIテンプレートのコミット `b1125d8839482cb7bbae603ddc6d0081bf87532e` から新規生成した独立チェックアウトを使用。

- Codex CLI 0.167.0、モデル `gpt-5.6-sol`、reasoning effort `low`
- LSPバイナリ：このPRの作業コード（`primeProjectSemantics` の通知リビジョンキャッシュを含む）でビルド
- 両条件で同じ `AGENTS.md`。LSP接続時には意味的な問い合わせを行うよう指示する **guided** 評価（自然選択ではない）
- 各課題1回ずつ。ランダムな揺れ・モデル側の行動差を排除できない探索的な比較

## 採点と制約

**独立動作採点は未完了。** 採点環境に `fastapi` がなく、両条件とも `ModuleNotFoundError` により採点を開始できなかった。**falseを不合格コードの証明として扱わない。** また、元の固定FastAPIコミットの `backend/app/api/deps.py` 36行目には `except InvalidTokenError, ValidationError:` というPython 3の構文エラーが存在する。これは両条件共通の既存問題であり、動作採点を別途正常化する必要がある。

- `rg` とLSPとの比較ではなく、あくまで **Codex全体の作業効率**。
- 試行回数は各課題1組のみ。統計的な優位性は判定できない。
- 実際の変更差分が一致したため、この条件ではLSPによる変更品質向上を示せない。
- 入力トークンにはキャッシュが大きく寄与する。未キャッシュ入力を重視する。
- `rename_password` のMCP初回失敗は正しい引数検証だが、エージェントがツール引数を正しく組み立てられなかったUX上の問題でもある。
- LSP側がプロジェクト操作の最適な経路（意味的rename）を選んでいないため、現時点ではLSPの性能限界と断定できない。

## 判定

**製品全体の優位性は未実証。** この2組の実操作ではLSP接続側の未キャッシュ入力が大きく、追加探索・余分な指示・ツールカタログ読み込み等の要因を切り分ける必要がある。内部単体ベンチマークの高速化だけではCodexの作業効率は向上しない。

次はMCPのツール選択・結果の小型化と意味的編集の利用率を改善したうえで、複数の実コードベースで反復・順序入替して比較する。
