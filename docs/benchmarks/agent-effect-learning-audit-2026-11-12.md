# AIエージェント実開発における学習サイクルの監査（2026-11-12）

## 結論

**100回中7回を、実際のCodex A/B比較→原因分析→製品または評価方法の修正→新しいA/B比較として確認**しました。50回のMCP単体動作検証や単なるモデル呼出は、この7回にも100回の目標にも含みません。

- 7サイクル、各サイクルで修正前後2ペア＝**14ペア・28回のAI開発試行**について、元のtraceとモデル使用量、初期Git状態、正解採点を突合
- 修正後の7ペアでは **7件で作業時間短縮**。少数・対象選択済みの実測であり、開発全般への普遍的な効果は未証明
- **非キャッシュ入力に重み1、キャッシュ入力に重み0.1を付けた参考試算では改善3件、悪化4件**。この重みは仮定であり、Codexのドル建て請求額を表すものではない
- 修正後のMCPはモデルから**9回実際に呼ばれ、9回とも正常完了**。呼出数だけを品質・生産性向上の証拠にはしない

## 検証方法の恒久的な修正

検証コードは [audit_agent_effect_cycles.py](audit_agent_effect_cycles.py)。従来、結果を説明文に手作業で写したことが誤った解釈につながりました。現在は次を自動的に突合し、矛盾があれば**そのサイクルを成功として集計しない**ようにしています。

- 修正前・修正後のそれぞれでCodex単体／MCP併用の両条件を実行し、4試行が実際に完了して独立正解判定に合格しているか
- 各ペアが同じ初期Gitコミット、同じモデル・推論強度に基づくか
- トークン集計と生トレースの最終使用量が一致し、非キャッシュ入力が総入力−キャッシュ入力であるか
- モデル問い合わせ回数・実MCP使用回数・成功したMCP呼出・実際に受け取った出力サイズを監査しているか
- 発見した問題・施した修正が明記されているか、修正後に実際にMCPが正常使用されたか
- 失敗、利用枠超過、初期条件の相違、単体API試験を進捗に水増ししていないか

評価スクリプト自体にも、値やログが改ざんされた場合は不合格になる回帰試験を追加しました。実際のプログラム修正と、評価方法の修正を区別します。

## 原因と改善：呼び出し関係調査の例

**問題**：`get_outgoing_calls` は、開発者の質問が「呼び出し先の名前とファイルのみ」であっても、範囲、シンボルID、呼び出し位置などを毎件出力していました。

**修正**：`hierarchy_view=name_path` を追加。表示に必要な関数名・ファイルパスと完全性メタデータだけを出力します。従来の完全表示はそのまま既定値に残しました。AI向けに「名前とパスだけで十分な場合は簡潔モード」という条件付き使用指針も追加しました。

| 同じLSP問い合わせ | 従来のfull応答 | name_path応答 |
|---|---:|---:|
| 応答サイズ | 5,691B | 986B |
| 正しい関数名・ファイルの組 | 15件 | 15件 |
| 情報量の削減 | — | **82.7%** |

実goplsから受けた結果を比較し、15件すべての関数名・パスが完全に一致することも確認しました。情報不足のまま結果を返すことはしません。

### 修正後、Codexが自ら簡潔なLSP呼出を選んだ比較

| 指標 | Codex単体 | Codex＋LSP |
|---|---:|---:|
| 独立採点 | 合格 | 合格 |
| 作業時間 | 23.617秒 | 12.788秒 |
| AIモデル呼出回数 | 4 | 3 |
| 総入力トークン | 73,144 | 63,781 |
| キャッシュ入力 | 62,720 | 43,904 |
| 非キャッシュ入力 | 10,424 | 19,877 |
| 実MCP呼出 | 0 | 1 (`get_outgoing_calls`) |
| MCP応答 | — | 986B |

**時間は45.85%短縮、総入力トークンは12.8%減、非キャッシュ入力は90.68%増**でした。したがって「MCPの返却を82.7%圧縮した＝非キャッシュ入力費用も82.7%減った」と言うのは誤りです。総入力の差もキャッシュ込みの割引請求額とは一致しません。

実際の料金表が取得できない場合、入力コストの判断は次の形で保留します。

`入力コスト相当値 = 非キャッシュ入力 + キャッシュ単価比率 r × キャッシュ入力`

- `r=0.1` と仮定すると、16,696対24,267相当で**LSP側の入力相当コストが45.35%増**
- `r=1` と仮定すると、73,144対63,781で**LSP側が12.8%減**
- 境界は `r≈0.5024`。ただし**出力トークン料金を含まない入力料金だけの境界**であり、真のドル料金・総額を意味しません

この違いが、先に「トークンが増えたのにLSPは効率的」と短絡的に説明してしまった原因です。今後はキャッシュ別使用量、問い合わせ回数、出力トークン、実効料金条件を揃えない限り、費用削減を断言しません。

## 同一製品・同一タスクを3ペア追加で反復

個別の1ペアのまま一般化しないため、簡潔モードのS04開発課題を、**同一モデル・同一MCPバイナリで3反復**しました。各反復はCodex単体とLSP併用の同じ初期Gitコミットから開始し、順序を交互にして、同じ独立した15件の正解照合を行いました。

| 3ペア平均 | Codex単体 | LSP併用 | 差 |
|---|---:|---:|---:|
| 正解 | 3/3 | 3/3 | 同等 |
| 作業時間 | 25.76秒 | 14.05秒 | **45.46%短縮** |
| 総入力トークン | 69,331 | 67,285 | 2.95%減 |
| キャッシュ入力 | 58,283 | 49,408 | 15.23%減 |
| 非キャッシュ入力 | 11,048 | 17,877 | **61.81%増** |
| 出力トークン | 985 | 478 | 51.49%減 |
| 入力費用相当値（キャッシュ比率r=0.1） | 16,876 | 22,817 | **35.20%増** |

3反復すべてでLSPの実呼出は**1回／試行**、呼出先は `get_outgoing_calls(hierarchy_view=name_path)`、MCPエラーはありませんでした。これは追加の同条件**確認試験**であり、修正を伴わないため100サイクルの追加回数には計上していません。

- [3ペア6試行の実測CSV](agent-effect-s04-compact-3pairs-2026-11-12.csv)
- 実行元の失敗や欠損は [独立A/B監査](audit_product_ab.py) で除外し、3ペアとも完全合格と判定しました

**改善したと言えること：** この対象課題では正確性を維持し、名前・パスだけが必要な質問へのLSP応答を小さくでき、AIの作業時間も短縮しました。**まだ改善できていないこと：** キャッシュ利用条件まで含む入力費用。低いキャッシュ単価比率ではむしろ高コストです。

## 現時点の課題

- この7回は互いに異なる開発課題（一部同じタスクの追加改善）であり、全体への汎化には不足
- 時間改善と費用改善は別軸であり、**費用相当値が悪化した4ケースを解決済みにしない**
- 修正前後のA/Bの実行時刻・ソース版が異なるため、2時点の時間差やトークン差を単独で因果効果と解釈しない
- 出荷判定には、より広い課題、多言語、3回以上の反復、実際のLSP使用と正解の証拠が必要
