# LSP利用改善の調査・修正・比較（2026-11-12）

**対象: simple-lsp-mcp のGoリネームとGo型エラー、各3ペア。一般的なLSP優位性の主張ではありません。** 実トレースは非公開の `.scratch/` に保管し、集計データは [CSV](product-ab-lsp-usage-remediation-2026-11-12.csv) で再確認できます。

## 事実と対応

1. Codexの既定 `coding` プロファイルでは、過去に成果を確認した `preview_rename` と `rename_symbol` が公開されていませんでした。**両方を追加し、14ツール構成に変更**。読み取り専用プレビューと明示的な書き込み許可を分離したままです。
2. 旧Codex traceではリネームプレビュー5,189Bと適用結果5,188Bのほぼ同内容を2回受信。`readable` モードで対象ファイルと変更件数、適用状態を残して重複を省き、**1,635Bと913B（合計約75%減）**にしました。`both` / `text` の完全JSONは互換維持し、完全プレビューの明示要求・エラー・警告も省略しません。
3. 型エラーに対してLSP自体が使用されていない試行がありました。実LSPで `get_diagnostics(path="internal/tools/engine.go")` が47行目の型不一致を正しく返すことを確認し、ツール説明と条件付き利用ガイドを改善。`readable` では診断のファイル位置・コンパイラメッセージを保った簡潔な表示にしました。
4. 実トレースではファイル未指定の診断を呼んで `complete=false` の結果を無駄に受信していました。既定 `coding` スキーマで **`path` を必須**とし、サーバー側でも省略を拒否。旧 `full` APIは互換維持し、不完全・未指定の結果は明確な警告を返します。実Codexアプリ経由で拒否を確認。
5. 旧トレースでは存在しない `symbol_path` を推測し、複数対象をまとめて問い合わせてエラーになった試行がありました。不明な関数名はまず `get_document_symbols(path)` で発見するようガイドを修正。独立評価では、失敗や `meta.complete=false` の呼び出しを「有益なMCP成功」として数えません。

- T43は時間**約39%短縮**、入力トークン**約7%減**。MCPは実際に選択・呼び出され、3回とも独立採点合格。ただし試行ごとのばらつきがあり、変更前評価との厳密な因果比較ではありません。
- T35は時間**約1.3%短縮**、入力トークン**約16%減**。LSP非利用の回も含むため**差をLSPの効果と断定できません**。直前の別試験では、パス未指定の診断と失敗した `inspect_symbol` を含む過剰呼び出しがあり、LSP接続側の時間・入力トークンの両方が悪化しました。それを分析して上記の修正につなげました。
- Codexのモデルと利用指示は各ペアで共通、同じ初期Gitハッシュから別作業コピーで実施。LSPの起動/ウォームアップはモデル作業時間から除き、指示はタスク条件付き。型エラー比較ではGoビルドキャッシュも各作業コピーで事前準備し、ウォームアップ時間を別記しています。これは自然選択だけのA/Bとは区別します。
- **今回のT35比較はサーバー側の「ファイル指定必須」修正を加えた後に開始しましたが、その後に追加したテスト・ガイド整備もあるため、全変更を含む最終配布物の性能再検証ではありません。**

## 出荷判定

Goの2課題では修正に進展がありましたが、残る言語・課題、再現性、全56タスク、Claude Code実モデル認証・公開リリースの条件は未達です。**Go型エラーで必ず速くなるとは確認されていません。** ソフトウェアが返す意味情報の有益性と、エージェントの総作業時間・トークン・精度は区別して判断します。
