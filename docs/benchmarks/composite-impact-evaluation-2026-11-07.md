# LSP高級ツールによる影響調査：実装・実測（2026-11-07）

## 検証内容

`investigate_change` は、指定したLSPシンボルの正確な宣言を解決し、参照先を深さ2まで追跡、呼び出し元の宣言と影響ファイルを重複排除して返します。

- `path` + `symbol_path` から、宣言シンボルツリーを**一度だけ取得**してグラフ探索へ渡します。元の「inspect_symbol→analyze_impact」で生じていた余分な取得を除去。
- `detail=files` は1対象のファイル・宣言と検証可能な制約情報。 `detail=graph` で全ノード・エッジ取得。
- `targets` 2〜6件により、別々の影響調査を**1回のMCP呼び出し**に集約できます。`detail=union` で詳細宣言を省き、各対象のファイル集合・参照件数・完全性と重複排除済みファイル集合を返します。
- 対象重複、混合パラメータ、無効な`detail`、不明なフィールドを検証し、部分的に成功しただけの情報を成功扱いしません。
- LSPの静的解析には限界があります。深さ制限や未対応参照を記録し、`meta.complete=false`を保持します。「影響なし」を断定しません。

## 注意点・次の課題

- 結果は2試行のみ。モデルの確率的な探索差や環境差は残る。
- 完了できないベースラインとの「作業時間の比率」は、同一成功品質を達成したコストの比較ではない。完了率を第一に報告する。
- **1回のCodexタスクに複数の調査を含めた**が、まだ複数タスクを続ける長期常駐セッションの比較ではない。LSP起動を償却する長期シナリオは未検証。
- `gopls references` 等のベースラインの選択コマンドが正しい宣言位置を指したか、異なる予算・制約がないかをログで監査する必要がある。無条件にgrep一般の限界とは解釈しない。
- 生トレースと結果はローカルの`.scratch/codex-investigate-*`に存在。サンドボックスでのGit作業ツリーや大量の元リポジトリをPRへ追加しない。
