- いずれも変更後 `git diff --check`、`go test -run '^$' ./lib/events`、APIモジュールの `go test -run '^$' ./types/events ./client` を確認。差分ファイル集合は、独立した3対象LSP一括renameの48ファイルと、除外されていた `lib/bpf/bpf.go` を合わせた49ファイルで判定。

## 実装側で見つけた欠陥・改善

### 1. コールドgoplsによるrename編集集合の変動

単純に `textDocument/rename` を呼ぶと、同じ対象でも初期ロードの段階で編集ファイル数が変動した。また `reflect.DeepEqual` で**生の編集順序**まで比較しており、実質同じ編集計画を不安定と誤認していた。

修正：
1. Goの `textDocument/references` を実行し、関連パッケージを先に読み込む。
2. 返されたWorkspaceEditを安全性チェック込みで正規化し、並べ替えた結果同士で比較する。
3. 収束を確認できない場合は**ファイル変更前に中止**する。

Teleportの3対象バッチで、対象順を入れ替えた4試行はすべて **48ファイル・162編集** と一致。実ファイルへの一括適用と主要モジュールの限定コンパイルも成功。

### 2. ビルド構成の違いによる変更漏れ

`lib/bpf/bpf.go` は `//go:build bpf` で通常の解析対象から外れていた。単一LSP renameの結果は45ファイル・157編集であり、それだけで全体完了とするのは誤り。

`unverified_build_tag_files`、`coverage_complete=false` を返し、`//go:build`、旧 `// +build`、GOOS/GOARCHのファイル名条件を考慮する。除外ファイルは**自動で文字列置換しない**。実goplsテストでも警告を確認した。

### 3. 独立インターフェース・受信者メソッド候補の発見

1つの `textDocument/rename` が同名の別インターフェースを更新しないことがある。新しい `unrenamed_method_candidates` はGo ASTにより、**LSPの編集対象に入らなかった宣言**のみを少量列挙する（上限16候補、生成コードは `generated: true` として後ろに並べる）。

Teleportの `IAuditLog/EmitAuditEvent` プレビューで実測した結果、`Emitter/EmitAuditEvent`、`Client/EmitAuditEvent` などを検出。同名のgRPC生成メソッドも存在したため、**同名だけで自動renameしてはならない**。候補は関連性未確認として警告する。これはGo構文解析による候補発見で、依存関係がLSPで証明されたという意味ではない。

この候補発見機能は上記Codex A/Bの**後に追加**した。Codexの呼び出し回数・トークンに与える効果はまだ未測定。

### 4. 評価スクリプトの破損と過大テスト

以前の実行ではCodexが広範囲のテストを実行して600秒でタイムアウトした。評価指示が途中で切れ、Pythonファイルには重複したスクリプト本体が残っていた。重複を除去し、限定コンパイルのみを要求する同一指示で両条件を再実行した。成功した結果だけでなく、この失敗も原因付きで区別する。

## 現時点の判断

**49ファイル規模の実際の変更作業で、同じ限定品質基準を満たしたうえでLSP追加による作業時間短縮と総入力削減を1組確認**した。ただし未キャッシュ入力は増え、性能・コスト削減があらゆる作業で成立する証拠ではない。

次の検証は、変更前の`preview_rename`で別のインターフェース候補を確認し、正しい対象のみを`targets[]`へまとめられるか、そしてそれがCodexの無駄な検索・複数回rename・未キャッシュ入力を減らせるか。生成済みgRPC/APIプロトコルを誤って変更しないことも正解条件に含める。
