# AIエージェント開発効果200サイクル：継続実行の設計（2026-11-13）

## この文書の目的

利用者が要求したのは、**Codex単体よりsimple-lsp-mcp併用が実際の開発を正しく・速く・効率よくできる状態に近づくよう、検証→原因分析→修正→同条件の再検証を200回実施すること**。MCPのAPIを200回呼ぶ、既存テストを200回繰り返す、200件の見せかけのタスクを作ることではない。

履歴を含む機械可読台帳：`docs/benchmarks/agent-effect-100-cycles-ledger.json`。**歴史的なファイル名は変更せず、`goal=200` が現在の要件。** 過去の有効記録は引き継ぎ、重複カウントしない。

## なぜ以前の進め方で終わらなかったのか：実行ログと設計の欠陥

1. **単発のチャット応答を永続ワーカーのように扱った。** 返信するとそのターンの処理は終了し、チャット自体では自律的に次の作業へ進めない。200回の目標をタスク管理に結び付ける前に途中で応答を終えた。
2. **一連の作業の成功条件を定義せず、API動作確認の50回を改善50回と混同した。** これは目的の取り違え。直接MCP呼出や同じ試験の単純反復は改善回数に含めない。
3. **モデル実行環境の前提を確認しなかった。** `.scratch/agent-effect-turn2-t34-before-20261113` の2026-11-13ログでは、両アームとも実モデルへの送信が `Operation not permitted (os error 1)` / `stream disconnected` で失敗し、入力トークン0。**localmcpのサンドボックス付きコマンド実行ではCodexへの外部通信が許可されていなかった。** その条件でA/Bを何度繰り返しても実験は進まない。
4. **未完了を継続できる制御が不十分だった。** タスク自動化は1時間ごとの別の実行であり、各回のコンテキストと時間には限界がある。欠損データや失敗試行が生じたとき、原因・次の一手・有効カウントを機械的に引き継ぐ必要がある。
5. **結果の解釈が偏った。** 作業時間の削減に目が行き、キャッシュ率や非キャッシュ入力の費用悪化を軽視し、評価器が本物のコードを誤判定したこともあった。

これらは「simple-lspの改善が200回不可能」だという証明ではない。**実行条件と品質管理が破綻していた**という、独立した問題である。

## 実施方式：200回を成立させる制御

**継続実行は既存のChatGPT自動タスク「simple-lsp 実効改善200サイクル」で行う。** 自動タスクの各回は短い実行単位とし、状態はリポジトリに保存する。タスクが起動しても、必ず最初に以前の台帳・エラー証拠・未解決の原因を読む。

- **排他制御：** 同一作業ツリーで並行実験しない。Linuxでは `flock -n .scratch/agent-effect-200.lock <command>` のように処理を囲み、ロック取得失敗時は二重実行せず終了する。Gitソースの作業場所と評価用隔離ワークスペースを分離する。
- **接続事前診断：** 実モデルA/Bを始める前にCodexの接続・認証・モデル利用可能性を1回確認する。**サンドボックス付きの`mcp__localmcp__execute` でCodex通信を試みない。実モデル呼出を伴うベンチは`mcp__localmcp__without_sandbox`（必要な承認を得た場合）でホストのネットワーク・認証を利用する。** 内部のCodex開発試行は従来どおり隔離ワークスペース・ネットワーク禁止を維持し、本体のネットワーク権限を開発コードに渡さない。
モデル通信の事前診断は、次の**実際の1モデルターン**を使用する。単なるCLIの起動成功では通過させず、`turn/completed` が成功し、正の入力トークンが記録された場合だけ実験へ進む。2026-11-13に同じホスト権限の実行で **connected=true / has_input_token_evidence=true** を確認した。

```bash
# このコマンド自体はCodexへの外部通信が許可されたホスト実行権限で実行する
python3 docs/benchmarks/preflight_agent_codex.py   --codex /path/to/codex   --codex-home /path/to/authenticated/CODEX_HOME   --workspace .
```

- **評価条件の事前固定：** 課題、正解の独立オラクル、モデル、effort、ソース版、warm LSP、許可ツール、停止条件を固定。実際のCodex単体 vs 同じCodex＋LSPを逐次比較し、**実装結果の正しさ**を独立に採点する。
- **因果的な問題修正：** 比較結果から「不要な結果、間違ったシンボル解決、MCP選択率、余分な呼び出し、テスト採点の誤り」など**実際に検出した欠陥**を一つ以上選び、修正して回帰試験する。何も直さない反復は完了回数にしない。
- **修正後の同条件A/B：** 新しい独立実行で両アームの正解・所要時間・モデル呼出回数・キャッシュ入力/非キャッシュ入力/出力・実MCP利用を取得する。悪化した指標も記録する。利用制限・ネットワーク失敗・不十分な採点の結果は失敗証拠として保存するが、成功サイクルを増やさない。
- **確定と引継ぎ：** 監査合格のときだけ台帳へ1件を追加し、証拠とソースを作業ブランチへコミット・pushする。無効試行は `uncounted_evaluations` へ記録。実行時間に達したら一貫したチェックポイントを残し、次回はその地点から再開する。ユーザーへの途中通知は行わない。
- **終了条件：** 200件を生ログで検証できたときだけ、次の最終専用コマンドを成功させる。利用制限のため中断した回数、作業開始回数、あるいは単純なモデル実行回数によってカウントを増やさない。

```bash
python3 docs/benchmarks/audit_agent_effect_cycles.py \
  --output .scratch/agent-effect-audit-200 \
  --require-goal 200 --require-complete
```

最終専用コマンドが失敗する間、完了通知は発行しない。このガードは、全サイクルの前後4試行、同じ初期ソース、正解採点、モデル使用量、実MCP呼出、重複した修正後証拠の再計上がないことを検査する。**0件や7件の状態で200件完了を宣言できない。**

## 現実的な制約

自動化はリクエスト時に毎回独立して稼働し、起動・ツール権限・モデル利用枠・接続性を保証しない。ローカルPCがオフラインなら実行できず、**サンドボックスからの外部通信拒否を回避できないとモデルの比較自体が行えない。** `without_sandbox` の承認が得られないときは強行せず停止し、正しい理由で無効試行として保全する。

また、**200件の有意義な製品改善が必ず存在するわけではない**。未修正の欠陥がない場合、見せかけの変更を作って件数を稼がない。200件の実験機会を確保しつつ、製品の性能上限・反例・トレードオフを誠実に扱うことが重要である。

現時点では「200回実行した」「200件改善した」あるいは「費用面でも有利」といった主張はしない。**持続的な実験・真正な監査・再開可能な記録**を確立したことと、実際に200回完了したことを区別する。
