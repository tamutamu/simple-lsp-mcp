# Codex 49ファイルrename：MCP応答量と未キャッシュ入力の検証（2026-11-08）

## 原因と対策

Teleport（約4,361 Goソース）を対象に、`IAuditLog.EmitAuditEvent` から `RecordAuditEvent` への49ファイルの実変更をCodexで比較した。

従来の15ツール `coding` から4ツール `refactor` へ絞るだけでは、未キャッシュ入力が必ずしも減らなかった。Codexのトレースを見ると、`preview_rename(preview_detail=full)` が約23.6KBの編集位置を返し、`investigate_change(detail=graph)` が約14.9KBのグラフを返していた。これらは影響の概観と関連インターフェースの選択段階では過剰。

実装した変更：
- `refactor` では `preview_detail=full` をツール定義から外す。`coding`/`full` の明示的な詳細モードは維持。
- `refactor` の影響調査は `detail=files|union` のみを公開し、巨大な`graph`を通常の選択肢から外す。
- `refactor` の `preview_rename` 出力は**変更ファイル名・編集件数・独立同名メソッド候補・未検証ビルドタグ・警告**に限定する。編集座標やサンプル位置は返さない。エンジンによる安全な編集計画の計算・検証は省略していない。
- 候補の同名メソッドについて、Go ASTから**上限180文字の署名（引数・戻り値）**を提供。監査イベント引数とgRPC `*events.OneOf` 引数を区別し、無関係な宣言の混入を減らす狙い。署名が一致しても依存関係の証明にはならず、候補の自動変更は行わない。

実際のレスポンス計測：
- LSP群のMCP出力合計は1組目14,273B・2組目14,450B。
- LSP群はプレビュー出力約7.7〜7.9KB、影響調査約3.0〜3.4KB、適用結果約2.7KB。
- 対照群のシェル出力は1組目約1.1MB（`gopls rename`の巨大なパッチ）、2組目約38KB。**baselineのばらつきが大きく、平均値は安定性の証拠ではない**。
- LSP群は両方とも最初に無関係な `GRPCServer.EmitAuditEvent` をバッチに含めて失敗し、対象を修正して一括renameに成功した。この失敗を減らすため上記の署名情報を追加した。

品質判定は、49対象ファイルの変更、`lib/events` とAPIモジュール関連の限定コンパイル、diffチェック、旧名の未変更箇所、無関係なgRPC宣言・生成コードの維持。タグ付き`bpf`コードはヘッダー依存関係のためコンパイルできず、全Goビルド構成での正常性を証明できていない。

これは**探索的な2組**。影響の全体的な正確性、コスト削減率の一般化や統計的有意性を保証するものではない。署名情報と最小要約の変更はこのA/Bの後であり、これら自体の改善効果をこの表に帰属させてはならない。

Codexの操作（署名付き最小プレビュー）：
- 1組目：`preview_rename`→`rename_symbol`の**2回**。MCP失敗0回。MCP返却テキスト7,827B。
- 2組目：`investigate_change`→`preview_rename`→`rename_symbol`の**3回**。MCP失敗0回。MCP返却テキスト11,090B。
- どちらも初回のrenameで関係のない `GRPCServer.EmitAuditEvent` を**指定しなかった**。同名ながら異なる `events.OneOf` と `events.AuditEvent` 引数の違いを、プレビュー署名から確認できる構成にした。
- 正しい49ファイル変更、`git diff --check`、主要Goパッケージの限定コンパイル、無関係なgRPC宣言・生成済みprotoファイルの未変更を、**両条件・両組とも検証**した。
- 対照群のシェル出力は1組目66,862B、2組目1,102,260B。`gopls rename`のパッチ出力に大きな差があり、対照群のモデル選択・出力量が平均削減率に影響している。

比較をまたいだ注意点：最小プレビュー追加と署名追加は同時に適用した。先の「従来の要約」2組とは**同一乱数シードや完全に一致するモデルの判断ではなく**、因果的な単独効果は測れない。今回のトレースで失敗がなくなったことは観測事実だが、署名追加だけが原因だと断定しない。

## 継続的な改善・評価の判断

今回確認できた製品上の価値は、**大規模コードで安全に完了した作業に対し、LSPが情報量の大きいシェル探索・個別編集・無関係な対象の再試行を減らせたこと**。一方、単一タスクの固定ベンチマーク・少数試行から、全言語・全規模での優位性は一般化しない。特に異なるビルドタグ設定、複数の独立インターフェース、別モジュール、gRPC生成コードなどは引き続き明示的に扱う。
