# LSPの選択・取得情報の再利用：問題分析と修正（2026-11-12）

**結論：LSPは必要な場面で使い、明示的な文字列検索で十分な場面では呼び出さないことが適切です。** すべての指標が必ず改善する、という主張はしません。

## 確認した問題と修正

1. シンボル一覧のreadable表示が最初はJSONより15.4%大きくなっていました。全行でパスを繰り返す設計を修正し、名前・種類・行番号・シンボルID・階層を保存。実際のMCP応答はJSON 2,920Bからreadable 2,156Bへ**26.2%減**。明示的なfull指定は完全JSONを維持。
2. inspect_symbolのコード断片をエージェントが再取得する理由の一つは、宣言開始行と前置文脈の開始行が区別されていなかったことでした。両行範囲を表示し、**編集していないソースは再利用、編集後は必要な範囲を再確認**する指示に修正。
3. find_referencesが42件の参照を返し、本番コードの呼び出し元2件以外はテストの参照でした。必要な場合に限りexclude_test_files=trueを指定できるよう実装。実Codex MCP呼出しは**42件・4,250B → 2件・234B（94.5%減）**。除外件数40を応答に明示。既定では全参照を維持。
4. 初期実装ではこの新しい引数をモデル向けMCPスキーマに登録し忘れていました。boolean型と引数説明を正式登録し、full/coding両プロファイルのテストを追加。
5. 実トレースでinspect_symbol(related)に上限200を指定してエラーになり、その後20件しか返らない部分結果を見てからrg/sedで調べ直すケースを確認。relatedは**最大20件の補助情報**であり、全参照の取得にはfind_referencesを選択するようツール説明・サーバー指示・エラーメッセージを修正。
6. T34は「tools.Newという明示的なセレクターの直接呼出しを探す」という課題でした。この場合はrgによる文字列検索の方が効率的で、ベンチマーク側のLSP優先案内が**無駄なLSP呼び出しを誘発**していました。案内を用途別に修正し、LSPの呼出ノルマを設けず、通常検索で十分なら使用しないよう改善。

## 品質と残課題

- 実goplsとの統合テストで、本番とテストファイル双方の同一シンボル参照を検出し、フィルター後に本番だけ残り除外件数が正しいことを確認。
- Python・TypeScript・JavaScript等のテストファイル名も単体テストで確認。未知の追加フィールドや不正情報は省略せず、JSONを返す方針です。
- 全参照と本番のみの参照は違う要求です。リファクタリングの影響範囲を調べる場合、テスト参照を除外してはいけません。
- 今回のMCP応答の縮小率は通信テキスト量です。モデルの総入力トークンや開発生産性の縮小率と同一視しません。
- Go以外の広範なA/B、長期的な効果、Claude Code実認証、正式出荷などの全56タスクは未完です。CIと元のユーザー作業ツリーは触っていません。

検証方法：Go 1.26.4、gopls、typescript-language-server、pyright-langserverをPATHへ導入し、SIMPLE_LSP_REAL_LSP=1でgo test -race ./... -count=1、go vet ./...。
