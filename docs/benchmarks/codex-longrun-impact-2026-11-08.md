# 大規模コードベース・連続工程におけるCodex＋LSPの実測（2026-11-08）

## 重要：Goキャッシュ権限を修正した再比較（最新・優先）

最初の評価ではCodex単独側の `gopls references` が空を返していた。
**Codexのworkspace-writeサンドボックスからホームの `~/.cache/go-build` に書き込めず、
`go/packages.Load` が失敗していた**のが原因。したがって過去のデータを
「単独では正確な参照を取れない証拠」として扱ってはいけない。

実装した修正：
- 両条件の各チェックアウトに `.bench-cache` を作り、`GOCACHE`、`XDG_CACHE_HOME`、`TMPDIR` をそこへ向ける。
- `shell_environment_policy.inherit=all` と `--approve-for-me` を両条件に適用。
- 計測用キャッシュは `.git/info/exclude` に追加し、コード改修と誤判定しない。
- 実際にCodexのシェルから `gopls references` がキャッシュエラーなしで**参照4件**を取得することを確認。
- トレースに `go/packages.Load`、`read-only file system` 等が現れた場合は
  `environment_valid=false` として、評価成功に含めない。

### 別経路で直接参照の件数も照合

ベンチマーク用高級LSPオラクルとは別経路の `gopls references`
CLIを、権限に問題のない通常環境で6宣言に実行した。

| 宣言 | gopls CLI | 高級LSPオラクル |
| --- | ---: | ---: |

| PostSessionSlice | 7 | 7 |
| SearchEvents | 11 | 11 |
| EmitAuditEventLegacy | 8 | 8 |
| GetSessionEvents | 10 | 10 |
| SearchSessionEvents | 9 | 9 |

この一致は**直接参照数の裏付け**であり、2ホップ全体のノード対応や
動的な影響を独立に証明したものではない。

**判定**：同一ソース・同一権限設定・`gopls`使用可能な条件でも、
高級ツールによる連続調査は正解に達し、作業時間と入力トークンを削減できた。
ただし通常群が3工程を正しく完了していないので「同等品質を達成した際の
時間・費用削減率」として一般化できない。たった2組の探索的試行である。

シェル検索0回、51.695秒、影響ファイル8件、影響宣言18件、直接参照4件を回答。
ファイル集合・件数は独立したオラクルと一致。
入力85,289トークン（うちキャッシュ済み72,064）。
ただし解析不完全の回答は説明文（文字列）で、真偽値ではなかった。
そこでMCPレスポンスに `incomplete` を**明示的なbool**として追加し、
元の `meta.complete` も維持した。追加後の実LSPで `incomplete: true`
の型と値を確認している。**この1試行だけで自然選択率を一般化しない**。

## 評価の狙い

LSPを常駐させ、複数工程の調査を1つのCodexセッションで処理すると、通常のコード探索よりもトークン・作業時間・正確性の面で優位かを確認した。CIの単体速度ではなく、**Codexの実作業そのもの**を計測。

- 対象: Teleport（Go、4,361ソースファイル）の固定チェックアウト。
- 3工程・6宣言: `EmitAuditEvent`、`PostSessionSlice`、`SearchEvents`、`EmitAuditEventLegacy`、`GetSessionEvents`、`SearchSessionEvents`。
- すべて `lib/events/dynamoevents/dynamoevents.go` のメソッド。正確な宣言位置はソースコードから計算し、**両群に同じ行・列情報**を渡す。
- 各宣言で参照を2ホップまで探索、最大30宣言、影響ファイル集合、影響宣言数、直接参照数、解析の完全性を報告。
- Codex 0.167.0、`gpt-5.6-sol`、low。両群で同じ `AGENTS.md`、同じ固定チェックアウト、`workspace-write`。ソース編集は禁止し、Gitのクリーン状態を確認。
- LSP群は最小のread-only `investigate` プロファイルを利用。**1つのCodex実行内で3回呼び出し、MCPプロセスと言語サーバーを使い続ける**。通常群はシェル＋goplsを利用できる。
- 合格条件は独立した事前収集LSPオラクルと全工程でファイル、宣言件数、直接参照件数、完全性が一致すること。ただしオラクルは同じLSPエンジンの個別問い合わせとの照合であり、別実装による完全な真値証明ではない。

## 見つかった設定・使い勝手の欠陥と修正

最初の連続実行ではLSP群が `path`、`symbol_path` と `line`、`column` を両方指定して1回失敗した。元の入力処理がこの自然な補足情報を競合する選択方式として拒否していたため。

- `normalizedInvestigationTarget` を追加。`path`＋`symbol_path` に正確な `line`＋`column` が併記された場合は、**宣言位置の整合性確認**として受け入れる。
- 位置が一致しない場合は `INVALID_ARGUMENT` を返す（誤ったシンボルを黙って選択しない）。
- 複数対象をまとめたときも重複検証が正常に動くようにした。
- 実際にTypeScript言語サーバーを起動したテストと、Teleport実ソースに対するMCP直接呼び出しで、正しい位置は成功・不正な位置は拒否を確認。

### 重要な限界

- 通常群の`gopls references`は、正確な宣言位置でも複数対象で空の結果を返している。通常群が正しく完了していない以上、**同等品質の成功タスクの速度差ではない**。他のCLI利用方法やIDE経由の参照取得と比較すべき。
- 「正確」の定義は同じLSPエンジンの独立呼び出し結果との一致。動的呼び出しや静的解析の限界があり、網羅的な全実行時影響の保証ではない。
- 各条件2回の探索的試行であり、統計的な有意性や他リポジトリへの一般化は示さない。
- **1回のCodexプロセス内の3工程**である。別々のユーザーターンを何時間も継続する永続プロセスの評価ではない。
- 言語サーバー初回起動時間は両群の計測から除外せず含めた。長時間作業での初期費用償却効果はさらに多工程の評価が必要。
- 実行トレース: ローカルの `.scratch/codex-longrun-teleport-fixed-20261108` と `.scratch/codex-longrun-teleport-reverse-20261108`（プライベートの実験環境をGitHubにアップロードしない）。
