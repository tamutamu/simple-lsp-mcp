# 事前登録型の開発効率評価（2026-11-01）

## 何を証明するか

製品の評価では、**利用指示の有無**と**MCPの効果**を混同しない。ベースラインとMCP利用条件を同じ課題・同じ反復番号でペアにし、同じタスクの繰り返しを独立な別課題として水増ししない。

### 成功条件（計測前に確定する）

- 20以上の独立した開発課題。これは最低の足切りで、十分な標本数を保証しない。
- 各課題・各条件で最低3回。新しいワークツリーと固定モデル設定、同一指示、独立採点器を利用。**全課題で同じ連続した反復番号（1〜N）を使用し、途中の欠番や特定課題だけの追加試行を認めない。** これは試行後の都合のよい反復追加を防ぐための最低限の検証であり、試験前に固定した課題・反復数の外部記録を代替するものではない。
- 両条件の合格率について、Wilson 95%信頼区間の下限が95%以上。
- **MCP呼び出しを試みただけでは不可**。MCP群の全試行で実際に成功した呼び出し（`valid_mcp_calls > 0`）が記録され、baselineではMCP呼び出しがゼロであること。テキスト形式のMCP応答に含まれるエラー、空応答も成功として数えない。トレース由来の成功件数が欠ける旧CSVは参考分析のみ可能。
- **試行の比較可能性を検証**。モデル名、推論設定、エージェントCLIバージョン、MCP実行バイナリのSHA-256、固定ソースコミット、指示ポリシーSHA-256、課題定義JSON SHA-256、独立採点器SHA-256が全試行で一致すること。メタデータが欠ける・不一致の場合は合格不可。自己申告のCSVだけでは採点の独立性を完全には証明できないため、元トレースと採点ログも保全する。
- **AGENTS.md / CLAUDE.md で利用を義務化した試験（`--selection-policy required`）を合格判定の対象とする**。MCP群の全試行で実際のMCP呼び出しが記録されていること。自然選択の補助試験（`natural`）なら80%以上のMCP利用を要求するが、製品利用の前提である必須指示を不当な失格条件にしない。
- 完了と独立採点を各試行で明示的に証明する `completed`/`graded` フラグが揃い、MCP側の観測合格率がベースライン以上。**独立採点プロセスの `grader_exitcode=0` も全試行で必須**。タイムアウト、異常終了、欠落した終了コードは成功扱いせず、旧CSVは探索用に限る。採点JSONの `success` は真偽値 `true` のみを成功とする（文字列 `"false"` は不可）。
- 失敗試行を選択的に再実行した結果を合格証拠にしない。全試行の `retry_count=0` が明示されること。`--resume --retry-incomplete` は診断用であり、再実行した試行は本評価に使用不可。旧CSVで試行履歴が欠落する場合も合格不可。
- **開発時間25%以上短縮、総入力トークン30%以上削減**。課題単位・等重みで集約した対数比率の、Bonferroni補正後の信頼区間**上限**がそれぞれ0.75/0.70以下となること（有意な微小改善だけでは不合格）。
- 上記条件を全部満たさなければ、偶然の改善やタスクの偏りを製品価値として「統計的に証明済み」と扱わない。

実行例：
```bash
python3 docs/benchmarks/analyze_codex_ab.py \
  --csv docs/benchmarks/codex-fastapi-ab-2026-11-01.csv \
  --study coding-required --selection-policy required
```

既存の2026-11-01データは独立課題が3つ、反復が2回であり、CSVに明示的な完了・採点フラグも含まれないので、**どれほど平均値が良くても不合格**になる。信頼区間は参考として出力する。

強制利用の有無は評価プロトコルで事前に固定し、試験結果を見てから `required` と `natural` を変更しない。実際のMCP呼び出しが発生しただけでは正確性・効率の改善は証明されない。必要な独立採点・十分な課題数・作業時間とトークンの二重基準は従来どおり必須とする。

## 評価タスク

比較軸は「Codex単独」「11ツールMCP」「19ツールMCP」。改善版の追加検証では、必要なら`--result-format text`と互換性重視の`both`を同じプロファイル・同じ利用指示で直接比較する。

性能評価には、単純な文字列検索だけでなく、同名シンボルの衝突、複数ファイルにまたがる定義・呼び出し・参照追跡、インターフェース実装、リネーム、既存APIの変更とE2E検証を含める。採点器は製品コードとは独立に実行する。

## 限界

このスクリプトのクラスターブートストラップは課題間の不確実性を対象にする。20課題で十分な検出力が保証されるわけではなく、理想的には事前にパイロット分散から検出力を見積もる。また全成功からのWilson下限は厳格な品質保証の完全な代替ではない。**成功条件を満たすまで標本を見ながら何度も検定して停止する行為（optional stopping）は禁止**し、標本数・採点条件を先に確定する。

MCP通信の小型化だけではエージェントのトークン削減の証明にならない。トークン実測にはCodex CLIの実利用記録が必要。

## パイロットに基づく事前標本数の目安

2026-11-01の11ツール群の3課題（各2反復）から、課題単位の対数効果量の標準偏差は作業時間 **0.071**、総入力トークン **0.074** と試算した。仮に5%の改善を検出したい場合、正規近似の簡易式 `n ≈ ((z(0.9875)+z(0.8))*σ/log(0.95))²` では約**18〜19独立課題**となる。ただし、この分散推定は独立課題わずか3件から得られており非常に不安定で、目安以上には扱えない。

独立課題30種類×各条件3反復（各条件90試行）を初期設計とし、品質のWilson下限や効果量を確認する。達成を保証するものではない。パイロットと本評価の課題は分離し、**本評価の標本数と判定基準は採点前に凍結**する。
