# 事前登録型の開発効率評価（2026-11-01）

## 何を証明するか

製品の評価では、**利用指示の有無**と**MCPの効果**を混同しない。ベースラインとMCP利用条件を同じ課題・同じ反復番号でペアにし、同じタスクの繰り返しを独立な別課題として水増ししない。

### 成功条件（計測前に確定する）

- 20以上の独立した開発課題。これは最低の足切りで、十分な標本数を保証しない。
- 各課題・各条件で最低3回。新しいワークツリーと固定モデル設定、同一指示、独立採点器を利用。
- 両条件の合格率について、Wilson 95%信頼区間の下限が95%以上。
- MCP接続条件の少なくとも80%で実際にMCPを使う（自発選択の評価を別に行う場合はその採用率も示す）。
- **作業時間と総入力トークンの両方**について、課題ごとに等重みで集約した対数比率の信頼区間上限が1.0未満。2つの指標の同時検定に対応するようBonferroni補正を行う。
- 上記条件を全部満たさなければ、偶然の改善やタスクの偏りを製品価値として「統計的に証明済み」と扱わない。

実行例：
```bash
python3 docs/benchmarks/analyze_codex_ab.py \
  --csv docs/benchmarks/codex-fastapi-ab-2026-11-01.csv \
  --study coding-required
```

既存の2026-11-01データは独立課題が3つ、反復が2回なので、**どれほど平均値が良くても不合格**になる。信頼区間は参考として出力する。

## 評価タスク

比較軸は「Codex単独」「11ツールMCP」「19ツールMCP」。改善版の追加検証では、必要なら`--result-format text`と互換性重視の`both`を同じプロファイル・同じ利用指示で直接比較する。

性能評価には、単純な文字列検索だけでなく、同名シンボルの衝突、複数ファイルにまたがる定義・呼び出し・参照追跡、インターフェース実装、リネーム、既存APIの変更とE2E検証を含める。採点器は製品コードとは独立に実行する。

## 限界

このスクリプトのクラスターブートストラップは課題間の不確実性を対象にする。20課題で十分な検出力が保証されるわけではなく、理想的には事前にパイロット分散から検出力を見積もる。また全成功からのWilson下限は厳格な品質保証の完全な代替ではない。**成功条件を満たすまで標本を見ながら何度も検定して停止する行為（optional stopping）は禁止**し、標本数・採点条件を先に確定する。

MCP通信の小型化だけではエージェントのトークン削減の証明にならない。トークン実測にはCodex CLIの実利用記録が必要。

## パイロットに基づく事前標本数の目安

2026-11-01の11ツール群の3課題（各2反復）から、課題単位の対数効果量の標準偏差は作業時間 **0.071**、総入力トークン **0.074** と試算した。仮に5%の改善を検出したい場合、正規近似の簡易式 `n ≈ ((z(0.9875)+z(0.8))*σ/log(0.95))²` では約**18〜19独立課題**となる。ただし、この分散推定は独立課題わずか3件から得られており非常に不安定で、目安以上には扱えない。

独立課題30種類×各条件3反復（各条件90試行）を初期設計とし、品質のWilson下限や効果量を確認する。達成を保証するものではない。パイロットと本評価の課題は分離し、**本評価の標本数と判定基準は採点前に凍結**する。
