# 開発シーン起点でLSP/MCPの価値を評価する設計

> 評価方針：LSPのツール名・速度から課題を作らず、開発現場のチケットを出発点にして、同じ成果物と品質条件で比較する。2026-11-08時点の実装23ツールを対象。従来のrename中心A/Bは補助証拠として保持する。

## 1. 何を評価するのか

「LSP呼び出しがrgより速いか」「返却バイト数が小さいか」は**内部実装の評価**に過ぎない。現場での関心は、事故を防げるか、調査を短縮できるか、仕様に対して安全な変更ができるか、複数工程で見落としが減るか。

- **第一優先：仕事の完遂**：要求された振る舞い、変更範囲、レビュー根拠を満たす。未完了・部分正解・偽陽性は「速い」と見なさない。
- **次：安全性と説明可能性**：無関係な実装を変更しない、未確認箇所を明示する、生成コード・別ビルド構成・動的ディスパッチの限界を説明する。
- **次：コスト**：総入力、未キャッシュ入力、出力、MCP/シェル操作数、手戻り・失敗、実時間。LSP初期化も計測に含め、連続タスクでは償却も分けて見る。
- **最後：現実的な利用率**：Codexはどの時点でLSPを選んだか、選ばなかったか、それが正しかったか。LSP必須の指示はしない。

## 2. 逆引きユースケース・マトリクス

| No. | チケット・困りごと | 有効と考えられるLSP/MCP | 比較する普通の手段 | 合格の中心 |
|---|---|---|---|---|
| C01 | 監査イベントの送信経路が複数ある。実装の場所を漏れなく調べたい | Implementation、Definition、Hover | rg、ソース/インターフェース読解 | すべての実装、関係ない同名メソッド0件 |
| C02 | 大きなアダプタの不要メソッドを削除してよいか調べたい | Diagnostics、References、Document Symbols | rg、Go AST、go vet | 未使用候補＋削除可否の留保、誤報なし |
| C03 | 一部のユーザーだけ権限エラー。API入口からチェックまで追いたい | Definition、Call Hierarchy、Inspect | rg、入口/認可ミドルウェア読解 | 実際の認可境界、再現条件、修正候補 |
| C04 | 運用障害の原因がどの呼び出し元に伝播するか調べたい | Incoming/Outgoing Calls、References | rg、コールサイト読解 | 呼び出し経路、例外/返値の扱い |
| C05 | 新しい担当者が巨大コードの責務分担を理解したい | Workspace/Document Symbols、Type Hierarchy | tree、find、rg、ファイル通読 | 関係するモジュールだけ抽出、誤った依存図を作らない |
| C06 | 公開APIの引数/型が変わる。破損する箇所を調査したい | Definition、Type Definition、References、Impact | rg、型チェック、テスト | 必要な変更箇所を特定、無関係な同名箇所を除外 |
| C07 | 複数インターフェースの契約変更を実装したい | Implementation、Rename、Preview、Diagnostics | rg、gopls CLI、手動編集とビルド | 変更後コンパイル、関連テスト、生成コード保持 |
| C08 | 大きな機能を直す前に回帰テスト対象を決めたい | References、Impact、Call Hierarchy | テスト名検索、依存検索 | 回帰テストの根拠、漏れと過剰の抑制 |
| C09 | 分析中にコンパイル/型エラーが生じた。最小修正が欲しい | Diagnostics、Code Action、Definition | go test、型エラーを読む、手動修正 | 失敗テストが通り、意味的な改悪がない |
| C10 | 外部ライブラリ更新で型・呼び出し仕様が変わった | Hover、Type Definition、References、Diagnostics | エラーログ、バージョン差分、検索 | 変更前後の契約一致、関連動作テスト |
| C11 | 既存レビューの差分で影響範囲/変更漏れを調べたい | References、Impact、Implementation | git diff、rg、部分ビルド | 具体的な漏れ/誤変更を検出できる |
| C12 | 未使用と思われる機能を段階的に廃止したい | References、Workspace Symbols、Call Hierarchy | rg、テスト、ロギング | 静的参照0でも動的/設定参照の可能性を留保 |
| C13 | 適用するQuick Fixが安全か事前評価したい | Code Action、Diagnostics、Preview | Linter/formatter、差分読解 | 診断解消、意図しない編集0件 |
| C14 | ファイル整形だけしたい（**LSPが負けてもよい対照**） | Formatting、Range Formatting | gofmt、prettier、Biome | 差分一致、速度/操作数で専用ツール有利でもよい |
| C15 | 単純な文字列・設定値の置換（**LSP不要対照**） | 原則使用しない | rg、sed、構成解析 | LSPを使わず正確に完了できるか |
| C16 | ビルドタグ・生成コード・動的登録が絡む変更（**LSPの限界**） | Diagnostics、Implementation、References | 複数ビルド設定、生成元調査、テスト | 除外構成を「解析完了」と偽らない |

この16シーンは**取り組むべき評価母集団の候補**であって、全シーンで実測済みではない。実証対象の採用は、再現できる課題と独立した合格条件を用意できたものに限る。

## 3. 比較の設計：ツールではなくチケットを共通化

**対照群 A：MCP未接続**。普通のシェル、rg、git、Go標準ツールに加え、Codexが自発的に使うならgopls CLIも使用可能（この場合「LSPなし」ではなく「LSP **MCPなし**」と呼ぶ）。

**処置群 B：同じ環境＋simple-lsp-mcp**。初回は`coding`（15ツール）を公開。対象を知った上で特定ツールを使うよう指示しない。必要なら`full`（23ツール）も別群で比較。4ツールの`refactor`は調査全般の評価には狭すぎる。

**厳密な「LSPなし」群 C**は、gopls CLI等の意味解析手段も取り除いた第三群として必要に応じて追加する。AとCを混同して効果を大きく見せない。

全群で固定コミット、同じ日本語の現場チケット、同じ `AGENTS.md`、同じモデル/思考設定、同じ権限/Goキャッシュ条件を使用し、独立したチェックアウトでペア実行する。開始順を入れ替え、失敗も保存。Codexが何を選び、何を試したかを追跡する。

### 品質ゲート

1. **調査**：実際の宣言/実装/呼び出し元を取り違えず、関係ない同名識別子を排除。実ファイルやAST、LSPとは別経路の証拠で検証。
2. **変更**：具体的な失敗テスト・期待する振る舞いで判定。必要範囲の無変更も確認。コンパイルが通っただけでは合格としない。
3. **レビュー**：候補は候補と明示し、動的呼び出しやビルドタグ・反射等の限界を含める。
4. **時間/トークン**：同品質で完了した試行同士に限って節約率を述べる。失敗率も別に表示する。

**評価基準のずれを防ぐ**：シーン単位で成果物を決め、必要以上に「参照件数が正確に何件か」といった内部LSPオラクルへの一致を要求しない。逆に、生成コード誤修正や見落としのような現実的な事故は正答判定に含める。人手でしか判定できない根拠の説得力は自動で合格扱いにせず、レビュー待ちとする。

## 4. 最初の実験対象（固定Teleport実ソース）

### C01 監査イベントの送信障害（Implementation中心）

- 実チケット形式：「ストリーミング送信だけ監査イベントが落ちる。通常送信との実装差を特定」
- **独立オラクル（対象を限定）**：Go標準ライブラリのAST走査で全Goモジュールの非テストソースを解析し、`context.Context`・`AuditEvent`型エイリアス・`error`戻り値の構文契約を検証。**明示された具象受信者メソッド24件**を確認（`go_emitter_oracle.go`）。これは全ビルドタグ構成や埋め込みで昇格するメソッドを完全に証明したものではない。
- 代表例：`api/client/auditstreamer.go` の `auditStreamer.EmitAuditEvent`、`api/client/client.go` の `Client.EmitAuditEvent`、`lib/events/emitter.go` の各種Emitter、`lib/auth/auth_with_roles.go`、DynamoDB/Firestore実装。生成gRPCの同名メソッドは引数が違うので除外。
- **スコープの限界**：「実装をすべて」という元チケットに`*_test.go`除外は明記されていない。再試行のLSP側が追加したテスト専用5件は実在する宣言であり、非テスト24件の厳格な採点では余剰だが無条件に誤検出とは言えない。次回は運用経路とテスト用実装を最初から分けて指定する。
- **重要な実測結果**：LSPの`textDocument/implementation`は同じリポジトリで2件のみを`complete=true`として返した。初期の「この2件が正解」という採点器は誤り。Codex単独は24件すべて見つけていた。Goの別モジュール間にある型エイリアスを無視してはならない。
- 不合格：`Emitter`というインターフェース宣言自体を具象実装と誤認する、無関係なgRPC `EmitAuditEvent` を混ぜる、ストリーマー側を欠く。
- 追加の人手レビュー：各実装がどのルートを通るかの説明は正しいか。

### C02 DynamoDB監査ログの保守レビュー（Diagnostics/References中心）

- 実チケット形式：「DynamoDBの大きいアダプタで、削除候補となる未使用メソッドを調べる」
- **本番処理からの参照がない候補**：`lib/events/dynamoevents/dynamoevents.go` の `Log.deleteAllItems` と `Log.deleteTable`。
- 直接確認：Go宣言、実goplsの`unusedfunc`情報診断（712行、745行）。しかし`dynamoevents_test.go`の76・85・109行で、AWS依存テストが**実際に呼び出している**。
- **重要な安全性**：「本番処理から未使用」と「削除してよい」は全く違う。ソースから呼び出しを見つけたCodex単独の『削除候補なし』という回答も、削除安全性という観点では妥当。最初に2件列挙したLSP側だけを正解とする自動採点は過度に単純化していた。
- Go compilerがこれを警告しない場合もある。baselineがrgやASTを用いて候補を見つければ正答。

### C03 GetUserの秘密情報アクセス拒否（Definition / Call Hierarchy中心）

- 実チケット形式：「本人の通常取得は通るが、`WithSecrets=true` で拒否される。gRPCから認可と取得を追う」
- 独立したコード上の境界：`lib/auth/grpcserver.go:431` の `GRPCServer.GetUser`（認証して委譲）、`lib/auth/auth_with_roles.go:1226` の `ServerWithRoles.GetUser`（RoleAdmin / currentUserAction / VerbRead 分岐、Identity.GetUserへ委譲）。
- 各分岐の説明を人手で評価し、単に2箇所を挙げただけでは十分な業務理解とは認めない。

対応するシナリオデータは `developer_scenarios.json`、ペア実行・追跡・自動採点は `run_developer_scenarios_ab.py`。自動採点は**実宣言の名前・パス・受信型・誤検出・未完了**に限定し、説明文の質・権限分岐の解釈は別途人手レビューする。

## 4.1 最初の評価で露呈した「品質基準の逆転」

最初のパイロットで`C01`の正解を**goplsが返した2件**だと誤設定したため、Codex単独が24件を答えたのに「不正解」、LSP側が2件を答えたのに「正解」という誤った採点になった。

そこでモデルの回答ではなく**別プログラムによるGo AST走査**で24件を再構築し、元のトレースを保持したまま再採点した。**Codex単独24/24、LSP側2/24**に評価が逆転する。

`api/go.mod`・`go.mod`等の複数Goモジュールが存在することをLSPツール自身も検出し、`find_implementations`は `meta.complete=false`・`requires_cross_module_review=true` と警告するよう修正。ただし**欠落した22件を自動で取得できるようになったわけではない**。完全性の虚偽主張を防ぐ緩和策であり、独立したモジュール横断解析が必要。

`C02`では、goplsの`unusedfunc`診断は本番コードに限ると妥当でも、`_test.go`から利用されるため「削除可能」を示していなかった。候補の検出、テスト参照の認識、削除の安全性を独立軸として評価する。

これは「LSPありの回答を正答扱いしてトークン差だけ測る」設計が成立しないことの実証でもある。

## 5. 次の拡大に必要な作業

1. C01/C02でA/Bパイロット実施。ツール利用はCodexが自然選択する。
2. C03/C04の原因追跡を同一案件の連続タスク化。Call HierarchyとDefinitionは自発的に使われるか、正しい境界を発見できるか。
3. C06/C08を改修の事前調査→テスト選定→修正→レビューという1つの長いチケットに結ぶ。
4. C09/C13は独立した失敗テストを用意し、Code Actionが安全に使えるか確認。
5. C14/C15の「LSPが不要・不利」な対照も必ず計測し、過剰利用や製品説明のミスを検出する。
6. Go以外にTypeScript/Pythonの実課題を追加し、特定のgoplsの強さだけを測ってしまう偏りを減らす。

## 判定

LSPは`rename`一機能の置き換えではなく、**調査、修正方針、実装、検証、保守レビュー**の全体に現れる「意味関係を正しく辿る能力」を提供する。正解率・誤変更率・証拠の質・手戻りの削減が本体であり、トークンと時間はその後に評価する。
