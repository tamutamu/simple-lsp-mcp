# 開発現場起点のLSP A/B：3つの実課題で分かったこと（2026-11-08）

## この評価はrenameを使わない

Teleportの固定リポジトリ（複数Goモジュールを含む、約4,361ソース）を用いた。開発者のチケットから課題を定義し、同一チケット・同一AGENTS.md・同じモデル/権限/Goキャッシュ条件の2群で比較。

- **MCPなし**：Codexの通常シェル、rg、Goコマンド、任意のgopls CLI。したがって厳密には「LSP完全なし」ではなく「simple-lsp MCPなし」と記す。
- **MCPあり**：上記にsimple-lspの`coding`プロファイル（15ツール）を追加。
- **モデル**：Codex CLI 0.167.0、`gpt-5.6-sol`、low。エージェントにはLSP/MCPの利用を強制しない。
- **成果物**：ソースを編集せず、必要な実装・不具合原因・安全性をパス、受信者、メソッド、根拠で回答する。生成したGoキャッシュは両群で同条件に除外。
- **真値の独立性**：Go AST、ソース中の型エイリアス、実際のテスト参照、権限判定のソースで確認。LSPが返した件数を真値として使わない。
- 各条件1回の**探索的パイロット**。統計的有意性を示さない。元のトレースと誤った初期グレードは上書きせず、別ファイルに再採点した。

## C01：LSP出力を正解扱いした評価が逆転

**本来の課題**：監査イベント送信がストリーミングの場合だけ失敗する。 `api/types/events/api.go` の `Emitter.EmitAuditEvent` の実装を、他の送信先も含めて調査。

最初のオラクルは、`find_implementations`の返した`api/client/auditstreamer.go`と`api/client/client.go`の2件を「全部」と誤って採用した。結果は「Codex単独が余計な22件を返したので失敗、MCPが2件なので成功」と採点された。

しかし `lib/events/types.go` にある
```go
AuditEvent = events.AuditEvent
Emitter = events.Emitter
```
は**型のエイリアス**であり、`lib/events`等の受信者が同じ`(context.Context, AuditEvent) error`契約を実装することがある。

LSPに依存しない`go_emitter_oracle.go`がGo ASTで全Goモジュールを走査（`*_test.go`除外、署名・エイリアス・戻り値を検証）した結果、**明示的なメソッド宣言24件**を確認。元のtraceを変更せずに`regrade_developer_scenarios.py`で再採点した結果は**Codex単独24/24、MCP 2/24**に逆転した。

ただしこれは静的構文の対象集合で、埋め込みによって昇格するメソッド、ビルドタグ差や実行時の配線まで網羅した「全ての実行可能な実装」の証明ではない。対象は**本番ソース内で明示された受信者メソッド**に限定して採点した。

### 製品への修正と同じチケットの再試行

複数Goモジュールで `textDocument/implementation` の1回の結果を「全ワークスペース完了」と宣言する問題を緩和するため、`find_implementations` の結果に以下を追加：

- 複数`go.mod`境界があれば `meta.complete=false`（結果件数上限による`truncated`とは区別）
- `requires_cross_module_review=true`
- 検出したGoモジュールのパスと、他モジュールの構造的実装を取りこぼし得る警告

実Teleportでは`api/go.mod`、`go.mod`などが検出され、警告が返ることを実LSPで確認。**LSP検索そのものが24件を返せるようになったわけではない。**

警告ありのA/B再試行では、MCP側のCodexが追加でソースを調べて24件を発見。一方、`*_test.go`の5型まで列挙したため、本番送信経路の判断には追加情報が増えた。Codex単独は24件に絞り、時間も短かった。

**採点上の追加の注意**：元のチケットは「すべての実装」と言っているが、テスト専用実装を除外するとは明記していなかった。この5型は実在するため、**LSP側の明白な誤答と断定してはいけない**。非`*_test.go`の24件を真値とするのは、運用中の送信経路という解釈を採用した**スコープ付きの自動採点**である。次の評価では「稼働経路とテスト専用の実装を区別して報告」と最初から指定する。成果物のスコープを結果を見てから変えてはいけない。

## C02：診断の「未使用」は削除可否と違う

`lib/events/dynamoevents/dynamoevents.go`でgoplsの情報診断 `unusedfunc` を受けるメソッド：
- `Log.deleteAllItems`（712行）
- `Log.deleteTable`（745行）

実際のコード検索では `dynamoevents_test.go` の**76/85行**で`deleteAllItems`、**109行**で`deleteTable`が呼ばれる。AWS依存テストのセットアップ・後片付けに必要。

- Codex単独はこのテスト参照を特定し、「未使用と断言できるメソッドはない」として`findings=[]`、ただし`limitations`で両メソッドのテスト使用を明記。
- MCP側は両方を**本番処理から未使用の候補**として返し、テストから呼ばれるため宣言だけを消してはいけないと明記。`get_document_symbols` / `inspect_symbol` / `find_references` を使った（`get_diagnostics`を選んだわけではない）。

**2件を列挙したかだけ**を判定すればMCP側が勝つが、「テストを壊さず削除できるか」の判断なら双方とも重要な事実を発見している。評価尺度を候補発見／本番参照／テスト参照／安全性に分解する。

## C03：自然な認可バグ調査ではLSPが選ばれない

`GetUser(WithSecrets=true)`が非管理者に拒否される原因を調査した。

- gRPC入口：`lib/auth/grpcserver.go:431` `GRPCServer.GetUser` は認証後に委譲。
- 認可境界：`lib/auth/auth_with_roles.go:1226` `ServerWithRoles.GetUser`。
  - `withSecrets=true` なら組み込みAdminロール判定。
  - `false` なら `currentUserAction`（本人など）または`VerbRead`。
  - 判定後に`authServer.Identity.GetUser(name,withSecrets)`へ渡す。
- 既定の取得実装：`lib/services/local/users.go` の `IdentityService.GetUser` は`withSecrets`でデータ取得経路を分け、通常取得で`LocalAuth`を消す。

両群とも正確な入口と認可境界を回答し、さらに多くの実関数を挙げて説明した。最初の「期待2メソッドと完全一致」採点は、適切な追加の調査結果11件を誤検出扱いしており不適切。`required_anchors`形式に直し、**追加した関数も実ソースの宣言と照合**するよう修正した。説明内容の最終的な妥当性は人手レビュー対象。

MCP側でもCodexはMCPツールを**0回**しか選ばず、シェルのみで調査を完了。このシーンで「LSPが速度・トークンを下げた」と主張するのは因果関係がない。

## 次の改善指針

1. 機能そのものの正確性を先にチェック。特にGoの複数`go.mod`構成における`find_implementations`のモジュール間欠落は未解決。
2. LSPの`complete=true`、`unusedfunc`のような**結果の適用範囲**を、機械的な合格基準として扱わない。
3. LSPが不要/不利な場面も正式な評価対象にする。自然なツール選択率はシーン別に確認。
4. 続いて**改修を伴う**シーン（バグ原因追跡→修正→回帰テスト）と、独立した失敗テストを使ったベンチマークを実施する。
5. C01/C02/C03は各条件1回。正確な成功率・費用削減率の一般化には、複数プロジェクトと反復が必要。
