# コア実装の機能・性能監査（2026-11-01）

## 判定

**根本実装の問題を確認。** 製品としてのLSPの優位性が実証できない理由をCodexの行動だけに帰してはならない。既存のシンボル照会・LSP文書同期・プロジェクト横断の候補探索には、重複処理、セッション管理の不具合、反復時の高コストなファイル走査が存在した。

## 確認した問題と対応

| 機能 | コード上で確認した問題 | 対応 | 判定 |
| --- | --- | --- | --- |
| `inspect_symbol(path,symbol_path)` | 対象ファイルが指定済みなのに、宣言解決後に文書シンボルツリーを再取得 | パス指定の宣言を1回のLSPツリーから解決。一括取得では同一ファイルのツリーを再利用 | 修正・CI確認済み |
| 文書同期 `document.Store.Sync` | 文書状態をファイルパスのみで管理。別サーバーで同じファイルを使っても`didOpen`を送らない | LSPセッションごとに独立管理 | 修正・回帰テスト確認済み |
| クラッシュ後のLSP再起動 | 新しいLSPプロセスに対して変更のない既存ファイルを再通知しない | 起動世代を記録。世代が変わった場合は`didOpen`で再同期 | 修正・回帰テスト確認済み |
| `didChange`失敗 | 通知前にローカル文書バージョンを増やすため、失敗後の再試行でバージョンが飛ぶ | 通知成功後のみバージョン更新 | 修正・回帰テスト確認済み |
| `find_references` / `find_implementations` / `rename_symbol` / 一部階層操作 | 初回だけでなく操作のたび、Python/TypeScriptの参照漏れ防止のため、プロジェクト全体の候補ファイルを調べる | 検索済み候補の二重`ReadFile`を`SyncBytes`で除去 | **全体走査は未解消** |

## 全体走査の根本原因

`internal/tools/warm.go` の `warmProjectSymbolCandidates` は、LSPのPython/TypeScript実装が未オープンのファイルからの参照を取りこぼすケースを避ける目的で、ソース全体を`filepath.WalkDir`して識別子文字列を含むファイルをLSPへ開く。これは意味解析結果を自作する処理ではないが、最大10,000ファイル・128MiBを**毎回の参照検索前に**調べるため、エージェント側がLSPを使うメリットを打ち消す可能性がある。

今回の修正で、一致ファイルについては探索時に読み込んだバイト列を`Docs.SyncBytes`に渡すため、同じファイルの二重ディスク読み込みはなくなる。一方、**探索時の全ファイル読み込み、ディレクトリ走査、追加のTypeScript意味解析準備リクエスト**は引き続き発生する。性能が改善した割合は実測していない。

## 次に検証すべきこと

1. MCPとLSPの各リクエストで、処理時間と`textDocument/documentSymbol` / `textDocument/references`等の呼び出し回数、ウォームアップ対象ファイル数・読み込みバイト数を測る。測定結果は秘匿情報を出さず集計のみ保存する。
2. ファイル追加・削除・編集・言語サーバー再起動でも参照漏れを生じない**確実な失効方式**を設計し、そのうえでプロジェクト全体の毎回走査を減らす。キャッシュの不正確な結果を高速化として採用しない。
3. 同名宣言、呼び出し階層、参照追跡、多言語構成の受入テストと、複数の独立した開発課題でCodex単独／MCPの品質・時間・トークンを比較する。

## 検証状態

GitHub Actionsで`go test ./...`、`go test -race ./...`、`go vet ./...`、Go/Python/TypeScriptの実LSP統合テストを通過。新しいCodexタスクA/Bはユーザー側ローカルMCPセッションがHTTP 429を返し使用できなかったため未実施。

**結論:** 基本実装に機能欠陥と明確な重複I/Oがあったことは確定。一方、「これらが総入力トークン増加の主因」「統計的な製品の有意性が達成された」はまだ証明されていない。
